# Technical Architecture & Design Document: v1.4.0 Dictionary Engine

## 1. System Topology & Architectural Layering

The v1.4.0 subsystem must follow the existing application architecture:

```text
Client Browser ──> Flask Route ──> Controller ──> Service ──> Repository ──> Database
```

The **Client Browser** is outside the backend application layers and communicates with Flask routes through HTTP requests. JSON responses may be used for asynchronous browser interactions where appropriate.

* **Flask Routes:** Routes handle HTTP-specific concerns and route requests to the appropriate controller. Routes must remain thin and pass required parameters explicitly to controllers. They are responsible for extracting the required request data and invoking the appropriate controller. Controllers must not access Flask's `request` object directly.
* **Controllers:** Controllers orchestrate application use cases and translate between HTTP-facing data and application operations. Controllers receive all required parameters explicitly from routes. They must not read from Flask's `request` object directly. They may construct HTTP-facing responses where appropriate, but business logic and persistence logic must remain in the service and repository layers respectively.
* **Services:** Services contain domain and business logic independently of Flask HTTP concerns and persistence details. Services handle validation boundaries, string tokenization, and syllable splitting for Hán Việt prediction, as well as the coordination of application workflows. Services must not depend on Flask request/response objects.
* **Repositories:** Repositories handle persistence and database access. Repositories contain targeted SQLAlchemy/SQL queries optimized to leverage appropriate database indexes. They must not contain business logic or authentication rules.
* **Authentication:** Admin access control is enforced at the appropriate Flask route boundary using the `@admin_required` mechanism. Authentication and authorization concerns must not be implemented in repositories. Services should only receive or evaluate explicit authorization information when a particular business use case requires an authorization decision.

### Architectural Boundary

v1.4.0 must extend these existing architectural boundaries rather than introducing a separate architectural pattern.

The application remains a server-rendered Flask web application. Asynchronous JavaScript and JSON responses may be used to support interactive web UI functionality, but v1.4.0 must not introduce a separate public API architecture, API versioning scheme, SPA framework, or frontend/backend separation unless explicitly required.

## 2. Component Execution Flow

When the Admin uses the dynamic creation workspace, mutations cascade cleanly across junction bridge tables to preserve relational data integrity.

### Asynchronous Duplicate Verification Pipeline

1. The frontend captures the text string typed into the main word input field.
2. An interactive JavaScript listener waits for a 400ms pause in typing (debounce window) before transmitting the query string to the dictionary duplicate-check backend route, following the existing application's route naming conventions.
3. The Flask route receives the HTTP request, extracts the required parameters, and passes them explicitly to the appropriate controller.
4. The controller orchestrates the duplicate-check operation and invokes the Word Service.
5. The Word Service requests the duplicate lookup from the Word Repository.
6. The Word Repository performs an indexed database lookup against the `viet_word` column.
7. If a matching record is found, the result is returned through the repository, service, controller, and route layers as a clean JSON summary containing `id`, `viet_word`, and `english_translation`.
8. The frontend uses the response to reveal the modification redirection alert banner where appropriate.

### Automated Hán Việt Prediction Engine

1. The Admin clicks the "Check for Existing Roots" action trigger on a compound word (e.g., *chính trị*).
2. The frontend sends the compound word to the appropriate dictionary backend route.
3. The Flask route extracts the required input and passes it explicitly to the controller.
4. The controller invokes the appropriate Service operation.
5. The Service parses the compound input string and splits it into an array of isolated lowercase component syllables (e.g., `["chính", "trị"]`).
6. The Service passes these lookup keys to the Repository.
7. The Repository executes a batch lookup against the `han_viet_roots` table using the indexed root string column.
8. The Service processes the returned data rows and separates the result into two explicit client arrays:
* **Found items:** Enabling an immediate "Associate" button action.
* **Missing items:** Enabling the inline "Add New Hán Việt Root" dialogue workflow.


9. The controller and route return the resulting data to the frontend as the appropriate JSON response.

### Hán Việt Root Association and Creation Flow

#### Existing Root Association

When an existing Hán Việt root is selected:

1. The frontend submits the dictionary word and selected root identifier.
2. The Flask route extracts the required identifiers and passes them explicitly to the controller.
3. The controller invokes the appropriate Service operation.
4. The Service validates that the dictionary entry and root exist and that the requested association is valid.
5. The Repository creates the corresponding `word_han_viet_association` record.
6. The database composite primary key prevents duplicate word/root associations.

#### Missing Root Creation

When a required Hán Việt root does not exist:

1. The frontend submits the dictionary word and new root data.
2. The Flask route extracts the required values and passes them explicitly to the controller.
3. The controller invokes the appropriate Service operation.
4. The Service validates the new root data.
5. The Repository creates the new `han_viet_roots` record.
6. The Service creates the corresponding `word_han_viet_association` record.
7. The unique constraint on `han_viet_roots.root` prevents duplicate roots.
8. The composite primary key on `word_han_viet_association` prevents duplicate word/root relationships.

### Hán Việt Root Unlink Flow

When an administrator removes a Hán Việt root association:

1. The frontend submits the dictionary word and root identifiers.
2. The Flask route extracts the required values and passes them explicitly to the controller.
3. The controller invokes the appropriate Service operation.
4. The Service validates that the association exists.
5. The Repository deletes only the corresponding `word_han_viet_association` record.
6. The associated `han_viet_roots` record remains available.

### Hán Việt Root Deletion Safety

Root deletion is an explicit administrative operation and must not rely on the database cascade as the mechanism for deciding whether deletion is allowed.

Before deleting a Hán Việt root, the Service must verify that no rows in `word_han_viet_association` reference the root.

* If associations remain, the deletion operation must be rejected.
* The administrator must instead remove the relevant associations through the unlink workflow.
* If no associations remain, the Repository may delete the root.

The `ON DELETE CASCADE` relationship on `word_han_viet_association.root_id` exists for referential cleanup but does not replace this application-level business rule.

### Dictionary Entry Modification Flow

1. The browser requests the selected dictionary entry.
2. The route passes the entry identifier to the controller.
3. The controller requests the complete entry and its relevant relationships from the Service.
4. The Service coordinates the required repository reads.
5. The server renders the modification workspace. The workspace supports updating dictionary word data, managing examples and their sources, and managing Hán Việt root associations.
6. Individual mutations are submitted through the appropriate backend routes.
7. The relevant controller invokes the corresponding Service operation.
8. The Service validates the requested change.
9. The Repository performs the persistence operation.

### Dictionary Entry Deletion Flow

Dictionary entry deletion is an explicit administrative operation.

1. The administrator requests deletion.
2. The interface requires explicit secondary confirmation.
3. The route authenticates the request.
4. The controller invokes the Service.
5. The Service validates the deletion operation.
6. The Repository deletes the dictionary entry.
7. Configured database relationships remove dependent word-type associations, Hán Việt associations, and contextual examples.

### Source Modification and Deletion Flow

Source management is performed through explicit Service operations.

* Existing sources can be selected for examples.
* New sources require a non-empty title.
* A source URL is optional.
* Deleting a source removes its associated contextual examples through the configured relationship.
* Deleting a source does not delete dictionary words.

## 3. Data Schema & Structural Integrity

The database tables are explicitly structured to maintain normalized schemas, clean deletion cascades, and efficient index traversal.

### Schema Relationships

* **Grammatical Classification:** One dictionary word can be associated with multiple grammatical or word-type classifications through the `word_type_association` bridge table. A word type can be associated with multiple dictionary words.
* **Hán Việt Root Association:** One dictionary word can be associated with multiple Hán Việt roots through the `word_han_viet_association` bridge table. A Hán Việt root can be shared by multiple dictionary words.
* **Contextual Examples:** One dictionary word can have multiple contextual sentence examples through `dictionary_examples`. Each example belongs to exactly one dictionary word.
* **Contextual Sourcing:** One source can be associated with multiple contextual sentence examples. Each example references exactly one source.
* **Example Lifecycle:** Deleting a dictionary word removes its associated examples through the configured database cascade relationship.
* **Source Lifecycle:** Deleting a dictionary source removes its associated examples through the configured database cascade relationship without deleting the dictionary words referenced by those examples.

### Table Definitions

#### Table: `users`

The `users` table is part of the v1.4.0 admin authentication implementation and stores the credentials required for the single-administrator login workflow.

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `id` | `INT`, Auto-Increment | Primary Key |
| `username` | `VARCHAR(50)`, Unique, Not Null | Account username |
| `password_hash` | `VARCHAR(255)`, Not Null | Cryptographically hashed password |

#### Table: `dictionary_words`

* **Indices:** `idx_viet_word_prefix` over (`viet_word`) to accelerate high-frequency autocomplete prefix inquiries.

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `id` | `INT`, Auto-Increment | Primary Key |
| `viet_word` | `VARCHAR(255)` `utf8mb4_unicode_ci`, Unique, Not Null | Target Vietnamese term |
| `english_translation` | `VARCHAR(500)`, Not Null | English definition |
| `created_at` | `TIMESTAMP` | Via TimestampMixin |
| `updated_at` | `TIMESTAMP` | Via TimestampMixin |

#### Table: `word_type_association`

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `word_id` | `INT`, Foreign Key (`dictionary_words.id` `ON DELETE CASCADE`) | Primary Key component |
| `word_type` | `VARCHAR(32)` | Primary Key component (Bounded via app business layer validation) |

#### Table: `dictionary_sources`

* **Indices:** `idx_sources_type_lookup` over (`source_type`) to speed up source-type lookup and grouping.

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `id` | `INT`, Auto-Increment | Primary Key |
| `source_type` | `VARCHAR(32)`, Not Null | Bounded via application enum tracking logic |
| `title` | `VARCHAR(255)` `utf8mb4_unicode_ci`, Not Null | Source title |
| `url` | `VARCHAR(2048)`, Nullable | Optional source web link |
| `created_at` | `TIMESTAMP`, Timezone Aware, Default: `CURRENT_TIMESTAMP` | Record creation timestamp |

#### Table: `dictionary_examples`

* **Indices:** `idx_word_examples_lookup` composite index over (`word_id`, `created_at`) to optimize chronological hydration and context counters.

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `id` | `INT`, Auto-Increment | Primary Key |
| `word_id` | `INT`, Foreign Key (`dictionary_words.id` `ON DELETE CASCADE`), Not Null | Associated word |
| `source_id` | `INT`, Foreign Key (`dictionary_sources.id` `ON DELETE CASCADE`), Not Null | Citation source |
| `sentence` | `TEXT` `utf8mb4_unicode_ci`, Not Null | Contextual example sentence |
| `english_translation` | `TEXT` `utf8mb4_unicode_ci`, Not Null | Translated example sentence |
| `created_at` | `TIMESTAMP` | Via TimestampMixin |
| `updated_at` | `TIMESTAMP` | Via TimestampMixin |

#### Table: `han_viet_roots`

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `id` | `INT`, Auto-Increment | Primary Key |
| `root` | `VARCHAR(50)` `utf8mb4_unicode_ci`, Unique, Not Null | Hán Việt root text |
| `chinese_character` | `VARCHAR(10)` `utf8mb4_unicode_ci`, Not Null | Corresponding Chinese character |
| `root_meaning` | `VARCHAR(255)`, Not Null | English meaning |

The `root` value must support Vietnamese diacritics and is constrained by application-level validation where applicable.

#### Table: `word_han_viet_association`

| Column | Data Type / Constraints | Description |
| --- | --- | --- |
| `word_id` | `INT`, Foreign Key (`dictionary_words.id` `ON DELETE CASCADE`) | Primary Key component |
| `root_id` | `INT`, Foreign Key (`han_viet_roots.id` `ON DELETE CASCADE`) | Primary Key component |

### Application Validation Rules

Application-level validation is handled by the Service layer before persistence operations are performed. Database constraints remain responsible for enforcing structural integrity and uniqueness at the persistence layer.

#### Dictionary Word Validation

* The Vietnamese word must not be blank.
* The word must conform to the application's allowed character rules.
* Duplicate dictionary words must be detected before creation.

#### Required Field Validation

* Required dictionary fields must be validated before persistence.
* A newly created source must have a non-empty title.
* Validation failures must prevent the corresponding persistence operation.
* Validation failures must be propagated to the calling controller so that the web interface can present appropriate feedback to the administrator. Invalid data must not be persisted.

#### Hán Việt Root Deletion Safety

Before deleting a Hán Việt root, the Service must verify that no rows in `word_han_viet_association` reference the root.

* If associations remain, the deletion operation must be rejected.
* The administrator must instead remove the relevant associations through the unlink operation.
* If no associations remain, the Repository may delete the root.

The database `ON DELETE CASCADE` relationship provides referential cleanup but is not relied upon as the business rule determining whether root deletion is permitted.

#### Association Unlinking

Unlinking a dictionary word from a Hán Việt root removes only the corresponding row from `word_han_viet_association`. The Hán Việt root remains available for other dictionary entries.

## 4. Comprehensive Testing Strategy

v1.4.0 must be covered by automated tests at the appropriate levels, using the project's existing testing conventions and infrastructure wherever applicable. The testing strategy should be pragmatic rather than requiring a specific test style for every component.

### Unit Tests

Unit tests may be used for localized logic where isolating the component provides a clear testing benefit. Mocks or other test doubles are acceptable when they meaningfully isolate the behavior under test, particularly for external dependencies or cases where testing a small piece of logic independently provides clearer coverage.

* **Target A: Domain Entity Constructors:** Validate domain object construction and structural constraints, such as ensuring that zero or negative IDs are handled according to the domain specification inside `HanVietRoot`.
* **Target B: String Sanitizers & Parsers:** Verify that the Hán Việt service correctly breaks compound words into tokenized syllable strings such as `["nghiệm"]` without losing accent markers.
* **Target C: Small, Isolated Business Rules:** Test self-contained validation or transformation logic independently when doing so provides meaningful coverage without unnecessarily reproducing repository or database behavior.

### Integration Tests

Where an established integration-testing pattern already exists in the project, new v1.4.0 functionality should follow that pattern rather than introducing a separate testing infrastructure.

For database-backed behavior, prefer the existing automated-test database and fixture infrastructure where practical. Tests should exercise real repository implementations and actual database constraints when the behavior being tested depends on persistence, relationships, indexes, transactions, or cascades.

* **Target A: Type Deletion Cascades:** Assert that deleting a row from `dictionary_words` removes all matching rows from `word_type_association` while preserving unrelated master dictionary entries.
* **Target B: Many-to-Many Bridge Mutations:** Verify that unlinking a root deletes the target row inside `word_han_viet_association` while preserving the core entry inside `han_viet_roots`.
* **Target C: Citation Source Cascades:** Ensure that deleting a source row from `dictionary_sources` removes its downstream child rows inside `dictionary_examples` through the configured database cascade constraints.
* **Target D: Repository Lookups:** Verify dictionary prefix searches, duplicate checks, Hán Việt root lookups, and other database-backed operations using the real repository implementation and the project's established database-test fixtures.
* **Target E: Dictionary Input Validation:** Verify that blank and invalid dictionary words are rejected before persistence and that valid words proceed.
* **Target F: Required Source Fields:** Verify that a source cannot be created without a title.
* **Target G: Hán Việt Root Deletion Safety:** Verify that a root with associations is rejected for deletion and that an unassociated root can be deleted.
* **Target H: Dictionary Entry Deletion:** Verify that deleting a dictionary entry removes dependent word-type associations, Hán Việt associations, and contextual examples through the configured relationships.
* **Target I: Hán Việt Root Creation and Association:** Verify that a new root can be associated with its originating dictionary entry and that duplicate word/root associations are prevented.

### Controller Tests

Controllers should be tested according to the project's established controller-testing pattern. Where controller behavior can be exercised directly without the Flask test client, prefer direct controller invocation with explicit parameters. The Flask `request` object should not be required by controller tests.

Controller tests should verify orchestration behavior, including parameter handling, service invocation, and construction of the expected result.

### End-to-End (E2E) Test Layer

E2E tests may use a headless browser runner such as Playwright to simulate important user journeys through the actual browser interface.

* **Target A: Admin Authentication Journey:** Navigate to the dedicated admin login page, enter valid credentials, confirm the authenticated admin state, and verify that Edit controls become available where appropriate.
* **Target B: Dynamic Creation Form Walkthrough:** Type a new term, confirm that duplicate-check feedback behaves correctly, fill the required structural type fields, add an example, and save the new dictionary entry.
* **Target C: Hán Việt Automation Interface:** Trigger root detection, associate an existing root, create a missing root where required, and verify that the resulting associations are reflected in the dictionary entry.

---

## 5. Testing Principles Summary

1. New tests should follow existing project conventions before introducing new testing patterns or infrastructure.
2. Reuse established fixtures and automated-test database infrastructure where applicable.
3. Prefer real implementations for database and repository behavior when an existing integration-testing pattern already provides this capability.
4. Use mocks or test doubles where they provide meaningful isolation or are otherwise appropriate for the behavior being tested.
5. Do not introduce a new test framework, test infrastructure, or testing abstraction solely for v1.4.0 without an identified requirement.
6. Tests should verify behavior at the layer where that behavior belongs rather than duplicating the same implementation logic across multiple test layers.
7. v1.4.0 implementation must not weaken or bypass the existing project's testing conventions merely for implementation convenience.
