# Technical Architecture & Design Document: v1.4.0 Dictionary Engine

## 1. System Topology & Architectural Layering

To enforce a clean separation of concerns and keep the Flask server highly efficient on a 1 GB RAM `t2.micro` instance, the subsystem is organized into a strict three-tier execution hierarchy:

* **Client Browser:** Handled via JavaScript asynchronously executing debounced API calls.
* **Orchestration Layer (Flask Blueprints/Controllers):** Acts as the system entry gate. Responsible for HTTP request deserialization, routing, enforcing the single-user `@admin_required` session cookie verification check, and serializing clean JSON payloads back to the client browser.
* **Service Layer (Domain Business Logic):** Executes programmatic data transformations independent of storage constraints. Handles string tokenization and syllable splitting for Hán Việt predictive sorting, manages validation boundaries, and coordinates workflows.
* **Repository Layer (SQLAlchemy / Raw Core Queries):** Direct database abstraction mapping. Contains targeted SQL queries optimized to leverage structural B-Tree database indexes. No business logic or authentication rules reside in this layer.

## 2. Component Execution Flow

When the Admin uses the dynamic creation workspace, mutations cascade cleanly across junction bridge tables to preserve relational data integrity.

### Asynchronous Duplicate Verification Pipeline

1. Frontend captures text string typing in the main word input field.
2. An interactive JavaScript listener counts a 400ms pause in typing (debounce window) before transmitting the query string to `/api/v1/dictionary/check-duplicate`.
3. The Orchestration controller accepts the payload, confirms session clearance, and routes the string straight to the Word Service.
4. The Service queries the Word Repository, which runs a lightning-fast indexed database lookup matching the `viet_word` column.
5. If a matching record hits, the backend returns a clean JSON summary container (`id`, `viet_word`, `english_translation`), triggering the frontend form layout to reveal the modification redirection alert banner.

### Automated Hán Việt Prediction Engine

1. The Admin clicks the "Check for Existing Roots" action trigger on a compound word (e.g., *chính trị*).
2. The Service layer parses the compound input string and splits it into an array of isolated lowercase component syllables (`["chính", "trị"]`).
3. The Service broadcasts these keys simultaneously down to the Repository layer.
4. The Repository executes a batch lookup against the `han_viet_roots` table matching the specific indexed root string column.
5. The Service processes the returned data rows, parsing the elements into two explicit client arrays: **"Found"** items (enabling an immediate Associate button action) and **"Missing"** items (enabling the inline Add New Hán Việt Root dialogue workflow).

## 3. Data Schema & Structural Integrity

The database tables are explicitly structured to maintain normalized schemas, ensuring clean deletion cascades and efficient index traversal over your low-footprint `t2.micro` database instance.

### Schema Relationships

* **Grammatical Profiling:** One word can map to multiple grammatical classifications via a dedicated composite primary key bridge table (`dictionary_words.id` $\rightarrow$ `word_type_association.word_id`).
* **Etymological Particles:** One word can map to multiple Hán Việt semantic particles via an explicit composite primary key bridge table (`dictionary_words.id` $\rightarrow$ `word_han_viet_association.word_id`).
* **Citation Containment:** One word owns multiple specific contextual sentence examples (`dictionary_words.id` $\rightarrow$ `dictionary_examples.word_id`). Deleting a core word cleanly sweeps away its downstream context data.
* **Contextual Sourcing:** One origin source tracks multiple distinct sentence examples (`dictionary_sources.id` $\rightarrow$ `dictionary_examples.source_id`). Deleting a source cascade-deletes all associated examples, keeping the base dictionary words intact.

## 4. Comprehensive Testing Strategy

To guarantee production resilience, features must pass automated checks across three isolated environments using **Pytest**.

### Unit Test Layer (Isolated Business Logic)

Unit tests evaluate localized modules and functions using mocks to isolate dependencies. They never touch the live MySQL instance or external clients.

* **Target A: Domain Entity Constructors:** e.g., validating that zero or negative IDs match structural specifications inside `HanVietRoot`.
* **Target B: String Sanitizers & Parsers:** verifying that the Hán Việt service correctly breaks compound words into tokenized syllable strings like `["nghiệm"]` without losing accent markers.
* **Target C: Security Access Logic:** confirming that `@admin_required` handles missing or malformed signed session cookies with a clean `403` response.

### Integration Test Layer (Database & Repository Boundaries)

Integration tests spin up a temporary, transactional test container to verify data transformations, constraint rules, and foreign key cascades.

* **Target A: Type Deletion Cascades:** asserting that dropping a row from `dictionary_words` instantly sweeps clean all matching rows in `word_type_association` while keeping the master word catalog intact.
* **Target B: Many-to-Many Bridge Mutations:** verifying that unlinking a root deletes the target row inside `word_han_viet_association` while preserving the core entry inside `han_viet_roots`.
* **Target C: Citation Source Cascades:** ensuring that deleting a source row from `dictionary_sources` cleanly sweeps away its downstream child rows inside `dictionary_examples` via the configured database cascade constraints.

### End-to-End (E2E) Test Layer (User Journey Automation)

E2E tests use headless browser runners (like Playwright) to simulate manual user behaviors in a visual layout pane.

* **Target A: Admin Authentication Journey:** navigating to the hidden login window, inputting credentials, confirming the UI profile status flips from Guest to Admin, and observing that Edit buttons render across the layout.
* **Target B: Dynamic Creation Form Walkthrough:** typing a new term, confirming the duplicate check alerts clear, filling structural type fields, adding an example, and clicking save.
* **Target C: Hán Việt Automation Interface:** clicking the root detection trigger and confirming that matching relational suggestions and missing root creation dialogue boxes render correctly on screen.
