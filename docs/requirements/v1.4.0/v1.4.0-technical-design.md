# Technical Architecture & Design Document: v1.4.0 Dictionary Engine

## 1. System Topology & Architectural Layering

The v1.4.0 subsystem must follow the existing application architecture:

```text
Client Browser ──> Flask Route ──> Controller ──> Service ──> Repository ──> Database
```

The **Client Browser** is outside the backend application layers and communicates with Flask routes through HTTP requests. JSON responses may be used for asynchronous browser interactions where appropriate.

* **Flask Routes:** Routes handle HTTP-specific concerns and route requests to the appropriate controller. Routes must remain thin and pass required parameters explicitly to controllers. They are responsible for extracting the required request data and invoking the appropriate controller. Controllers must not access Flask's `request` object directly.
* **Controllers:** Controllers orchestrate application use cases and translate between HTTP-facing data and application operations. Controllers receive all required parameters explicitly from routes. They must not read from Flask's `request` object directly. They may construct HTTP-facing responses where appropriate, but business logic and persistence logic must remain in the service and repository layers respectively.
* **Services:** Services contain domain and business logic independently of Flask HTTP concerns and persistence details. Services handle validation boundaries, string tokenization, and syllable splitting for Hán Việt prediction, as well as the coordination of application workflows. Services must not depend on Flask request/response objects.
* **Repositories:** Repositories handle persistence and database access. Repositories contain targeted SQLAlchemy/SQL queries optimized to leverage appropriate database indexes. They must not contain business logic or authentication rules.
* **Authentication:** Admin access control is enforced at the appropriate Flask route boundary using the `@admin_required` mechanism. Authentication and authorization concerns must not be implemented in repositories. Services should only receive or evaluate explicit authorization information when a particular business use case requires an authorization decision.

### Architectural Boundary

v1.4.0 must extend these existing architectural boundaries rather than introducing a separate architectural pattern.

The application remains a server-rendered Flask web application. Asynchronous JavaScript and JSON responses may be used to support interactive web UI functionality, but v1.4.0 must not introduce a separate public API architecture, API versioning scheme, SPA framework, or frontend/backend separation unless explicitly required.

## 2. Component Execution Flow

When the Admin uses the dynamic creation workspace, mutations cascade cleanly across junction bridge tables to preserve relational data integrity.

### Asynchronous Duplicate Verification Pipeline

1. The frontend captures the text string typed into the main word input field.
2. An interactive JavaScript listener waits for a 400ms pause in typing (debounce window) before transmitting the query string to the dictionary duplicate-check backend route, following the existing application's route naming conventions.
3. The Flask route receives the HTTP request, extracts the required parameters, and passes them explicitly to the appropriate controller.
4. The controller orchestrates the duplicate-check operation and invokes the Word Service.
5. The Word Service requests the duplicate lookup from the Word Repository.
6. The Word Repository performs an indexed database lookup against the `viet_word` column.
7. If a matching record is found, the result is returned through the repository, service, controller, and route layers as a clean JSON summary containing `id`, `viet_word`, and `english_translation`.
8. The frontend uses the response to reveal the modification redirection alert banner where appropriate.

### Automated Hán Việt Prediction Engine

1. The Admin clicks the "Check for Existing Roots" action trigger on a compound word (e.g., *chính trị*).
2. The frontend sends the compound word to the appropriate dictionary backend route.
3. The Flask route extracts the required input and passes it explicitly to the controller.
4. The controller invokes the appropriate Service operation.
5. The Service parses the compound input string and splits it into an array of isolated lowercase component syllables (e.g., `["chính", "trị"]`).
6. The Service passes these lookup keys to the Repository.
7. The Repository executes a batch lookup against the `han_viet_roots` table using the indexed root string column.
8. The Service processes the returned data rows and separates the result into two explicit client arrays:
* **Found items:** Enabling an immediate "Associate" button action.
* **Missing items:** Enabling the inline "Add New Hán Việt Root" dialogue workflow.


9. The controller and route return the resulting data to the frontend as the appropriate JSON response.

## 3. Data Schema & Structural Integrity

The database tables are explicitly structured to maintain normalized schemas, clean deletion cascades, and efficient index traversal.

### Schema Relationships

* **Grammatical Profiling:** One word can map to multiple grammatical classifications via a dedicated composite primary key bridge table (`dictionary_words.id` → `word_type_association.word_id`).
* **Etymological Particles:** One word can map to multiple Hán Việt semantic particles via an explicit composite primary key bridge table (`dictionary_words.id` → `word_han_viet_association.word_id`).
* **Citation Containment:** One word owns multiple specific contextual sentence examples (`dictionary_words.id` → `dictionary_examples.word_id`). Deleting a core word cleanly sweeps away its downstream context data.
* **Contextual Sourcing:** One origin source tracks multiple distinct sentence examples (`dictionary_sources.id` → `dictionary_examples.source_id`). Deleting a source cascade-deletes all associated examples, keeping the base dictionary words intact.

## 4. Comprehensive Testing Strategy

v1.4.0 must be covered by automated tests at the appropriate levels, using the project's existing testing conventions and infrastructure wherever applicable. The testing strategy should be pragmatic rather than requiring a specific test style for every component.

### Unit Tests

Unit tests may be used for localized logic where isolating the component provides a clear testing benefit. Mocks or other test doubles are acceptable when they meaningfully isolate the behavior under test, particularly for external dependencies or cases where testing a small piece of logic independently provides clearer coverage.

* **Target A: Domain Entity Constructors:** Validate domain object construction and structural constraints, such as ensuring that zero or negative IDs are handled according to the domain specification inside `HanVietRoot`.
* **Target B: String Sanitizers & Parsers:** Verify that the Hán Việt service correctly breaks compound words into tokenized syllable strings such as `["nghiệm"]` without losing accent markers.
* **Target C: Small, Isolated Business Rules:** Test self-contained validation or transformation logic independently when doing so provides meaningful coverage without unnecessarily reproducing repository or database behavior.

### Integration Tests

Where an established integration-testing pattern already exists in the project, new v1.4.0 functionality should follow that pattern rather than introducing a separate testing infrastructure.

For database-backed behavior, prefer the existing automated-test database and fixture infrastructure where practical. Tests should exercise real repository implementations and actual database constraints when the behavior being tested depends on persistence, relationships, indexes, transactions, or cascades.

* **Target A: Type Deletion Cascades:** Assert that dropping a row from `dictionary_words` removes all matching rows from `word_type_association` while preserving unrelated master dictionary entries.
* **Target B: Many-to-Many Bridge Mutations:** Verify that unlinking a root deletes the target row inside `word_han_viet_association` while preserving the core entry inside `han_viet_roots`.
* **Target C: Citation Source Cascades:** Ensure that deleting a source row from `dictionary_sources` removes its downstream child rows inside `dictionary_examples` through the configured database cascade constraints.
* **Target D: Repository Lookups:** Verify dictionary prefix searches, duplicate checks, Hán Việt root lookups, and other database-backed operations using the real repository implementation and the project's established database-test fixtures.

### Controller Tests

Controllers should be tested according to the project's established controller-testing pattern. Where controller behavior can be exercised directly without the Flask test client, prefer direct controller invocation with explicit parameters. The Flask `request` object should not be required by controller tests.

Controller tests should verify orchestration behavior, including parameter handling, service invocation, and construction of the expected result.

### End-to-End (E2E) Test Layer

E2E tests may use a headless browser runner such as Playwright to simulate important user journeys through the actual browser interface.

* **Target A: Admin Authentication Journey:** Navigate to the hidden login page, enter valid credentials, confirm the authenticated admin state, and verify that Edit controls become available where appropriate.
* **Target B: Dynamic Creation Form Walkthrough:** Type a new term, confirm that duplicate-check feedback behaves correctly, fill the required structural type fields, add an example, and save the new dictionary entry.
* **Target C: Hán Việt Automation Interface:** Trigger root detection and confirm that matching relational suggestions and missing-root creation dialogue boxes render and behave correctly.

---

## 5. Testing Principles Summary

1. New tests should follow existing project conventions before introducing new testing patterns or infrastructure.
2. Reuse established fixtures and automated-test database infrastructure where applicable.
3. Prefer real implementations for database and repository behavior when an existing integration-testing pattern already provides this capability.
4. Use mocks or test doubles where they provide meaningful isolation or are otherwise appropriate for the behavior being tested.
5. Do not introduce a new test framework, test infrastructure, or testing abstraction solely for v1.4.0 without an identified requirement.
6. Tests should verify behavior at the layer where that behavior belongs rather than duplicating the same implementation logic across multiple test layers.
7. v1.4.0 implementation must not weaken or bypass the existing project's testing conventions merely for implementation convenience.
